Abstract Interfaces in CMAS

Concept and purpose

An abstract interface represents a capability or set of skills that can be provided by one or more resources in the system, without specifying which exact resource will execute them.

The main idea is to separate what should be done from who performs it. This allows the Planner Agent to dynamically locate and allocate a suitable resource during runtime.

By using abstract interfaces, developers can write code that is resource-independent and goal- or skill-driven, while the system automatically handles resource selection, negotiation, and execution sequencing.

An abstract interface can be seen as a virtual handle or placeholder for a capability. When a skill of an abstract interface is accessed for the first time, the system negotiates with all compatible resources and selects the most suitable one based on cost, availability, and other constraints.

It is also possible to explicitly trigger this negotiation using:

abstract_name.negotiate()

Note
If negotiation is not triggered explicitly, the system performs negotiation automatically the first time the interface is accessed.

Mental Model

A useful way to think about an abstract interface is as a request for a capability rather than a specific resource.

Instead of calling a particular robot or machine directly, the program simply requests a capability through the interface.

For example:

Robot.Pick();
Robot.Leave();

The program does not specify which robot should perform the operation.
During negotiation, the system searches for available resources that provide the required skills and selects a suitable one.

Once a resource has been selected, the abstract interface acts as a handle to that resource. All subsequent calls through the interface will be executed on the same resource until a new negotiation is performed. This makes it possible to write programs that focus on the required operations while the system automatically manages resource selection and allocation.

Plug & Produce support

Abstract interfaces also support the concept of Plug & Produce.

Since programs are written against capabilities rather than specific resources, new resources can be deployed or undeployed during runtime without requiring changes to the program logic. When a new resource becomes available, it can participate in the negotiation process and may be selected if it provides compatible interfaces with a lower cost or better availability.

Similarly, if a resource is removed or becomes unavailable, the system can renegotiate the abstract interface and bind it to another compatible resource. This makes it possible to build flexible automation systems where resources can be added, replaced, or removed dynamically while the running programs continue to operate.

Declaring abstract interfaces

You declare an abstract interface in Structured Text using the following syntax:

abstract [handle] <name1> [, <name2>, …] : interface;

name1, name2 … are the names of the abstract interfaces.

Adding the optional handle modifier allows special management of the interface (see interface declaration details).

After declaration, skills can be accessed through the abstract interface, for example:

name.MoveTo(); name.Use();

When the interface is accessed for the first time, the Planner Agent will automatically negotiate and bind the interface to a suitable resource.

Example 1: Simple abstract interfaces

Program AbstractExample;
{ Abstract remote interfaces }
abstract Robot, Resource : interface;
Begin
Robot.MoveTo();
Resource.Use();
Resource.Signal := TRUE;
Resource.Motor();
End.

Example 2: Abstract interface with handle modifier

Program AbstractHandleExample;
abstract handle transport : interface;
var returnValue: integer;
function onRun() : integer;
begin
transport.negotiateandbook();
transport.moveRight(returnValue);
repeat
sleep(100);
until returnValue = processplan.running;
transport._unbook();
onRun := returnValue;
end.

Defining local interfaces

You can also define local interfaces to describe the variables and skills required for matching with remote interfaces. This is useful when the interface is not pre-configured in the system.

Syntax 1: Define a new local interface

define [handle] <name> : interface; begin var x, y, z : real; function move; end;

Example

Program DefineExample1;
define aRobot : interface;
begin
var x, y, z : real;
function move;
end;
begin
aRobot.x := 2;
aRobot.y := 3;
aRobot.z := 0;
aRobot.move();
end.
Note
For more details about declaring abstract interfaces see interface declaration details.

Resource binding after negotiation

Once an abstract interface has been negotiated and bound to a resource, all subsequent skill calls on that interface will be executed on the same resource.

For example, if an abstract interface name represents a robot:

name.Pick();
name.Leave();

The Planner Agent ensures that both Pick() and Leave() are executed on the same physical robot.

This guarantees consistent state and coordination, which is essential for tasks that require multiple sequential operations on the same resource.

The resource binding remains valid until a new negotiation is explicitly triggered or the interface is reset by the system.

Interface validation during negotiation

During negotiation, the Planner Agent verifies that a candidate resource is compatible with the abstract interface.

This compatibility check includes:

Variable matching
All variables defined on the abstract interface must exist on the candidate remote interface. Their types and value ranges must also be compatible.

Skill availability
All skills that are called through the interface must exist on the remote interface and be executable.

Only resources that satisfy these conditions are considered valid candidates.

If multiple compatible resources are found, the Planner Agent selects the resource with the lowest cost. This ensures that abstract interfaces always map to resources that can fully satisfy the expected capabilities and constraints.

Local abstract interfaces

The primary purpose of an abstract interface is to enable dynamic binding to the most suitable remote interface. However, in some situations, it is useful to bind to a local interface within the same agent.

This pattern can be used when multiple external interfaces act as receivers of skill calls, while the actual execution logic is centralized in a single internal interface. The internal interface then acts as the owner of the real implementation, ensuring consistent behavior and simplified coordination.

By routing all calls through a local internal interface, it is possible to:

  • Centralize execution logic
  • Maintain consistent state handling
  • Coordinate multiple incoming requests in a more controlled manner

This pattern is particularly useful in combination with interfaces that expose a ParallelCapacity greater than one. In such cases, multiple interface instances may receive concurrent skill calls, while the internal interface ensures that execution is properly synchronized and scheduled according to the resource agent’s logic.

Using the define local modifier is a convenient pattern to explicitly create an interface that is intended to resolve locally rather than through remote negotiation.

Program Processplan;
var counter := 0 : integer;
define local internal : interface;
begin
var PartName : String;
function run;
end;
function onRun() : integer;
begin
internal.PartName := inttostring(agent.counter);
internal.run();
onRun := processplan.done;
end.
Note
When used together with ParallelCapacity, multiple external interface instances may invoke the same internal interface concurrently. The resource agent is then responsible for defining how these requests are prioritized and executed.
