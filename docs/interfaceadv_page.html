Advanced Interface Concepts

Parallel Interfaces

An interface can serve one remote interaction at a time. When booking is used (which is the preferred approach in many situations), the interface is reserved and other agents must wait until it is unbooked. In most cases, this behavior is sufficient since other agents will simply wait until the interface becomes available. However, in scenarios where multiple requests must be handled concurrently, it is possible to expose multiple identical interface instances. This can be achieved by setting the ParallelCapacity property on a resource interface. The ParallelCapacity defines how many parallel instances of the interface can be active at the same time. During runtime, the agent will create multiple identical interface instances based on this value. Each instance behaves as an independent interface and can be negotiated and booked separately. This allows multiple agents to interact with the same type of resource in parallel, while still maintaining controlled access to each individual interface instance.

Interface Queues

When multiple agents attempt to access a single interface, the onNegotiate() function is called to decide whether a request should be accepted or rejected. By default, requests are processed in a first-come, first-served manner. However, the resource agent can implement custom logic to control how requests are prioritized and executed. By setting the interface property QueueRequest to true, the global interface variable queue (as defined in queue.inc, see structure text include) is enabled. The members of the queue are listed in the table below. When enabled, the onQueue() function is called before onNegotiate(), allowing the agent to inspect and manage incoming requests. The onNegotiate() function can then use this information to make more informed decisions.

Name Type Description
agentreference reference Reference to the agent that initiated the negotiation process
interfacereference reference Reference to the interface on agentreference that is requesting access
time integer Relative time (ms) when the negotiation request was created. Can be used to compare requests
value integer Default value is 0. Can be used freely to support custom prioritization logic

This mechanism allows the resource agent to determine execution order based on priority, cost, timing, or other criteria. To avoid resource conflicts and ensure consistent execution, all accepted requests can be routed to a local internal interface that coordinates the execution.The queue grows dynamically as more agents attempt to negotiate up to a max size. The current negotiation attempt is always placed at the top of the queue.

Note
The negotiation mechanism is reactive and operates on the current request only. While the queue provides visibility of multiple pending requests, the onNegotiate() function can only accept or refuse the request currently being evaluated. Multiple negotiation attempts from the same agent and interface do not create duplicate entries in the queue. Instead, the existing entry is updated and may move within the queue based on the new request.

It is not possible to directly select or accept a request at another position in the queue then the first one (top). For example, if a more suitable request exists deeper in the queue, the current request must be refused. The preferred request must then initiate a new negotiation attempt in order to be reconsidered.

This implies that prioritization strategies must be implemented indirectly by:

  • Refusing lower-priority requests
  • Allowing higher-priority requests to retry and reach the top of the queue

As a result, scheduling behavior emerges over time rather than being explicitly controlled in a single decision step. This behavior reflects the real-time nature of the system, where decisions are made incrementally as requests arrive.

Note
Queue entries are not explicitly removed when a request is refused. Instead, entries become outdated over time. The time field can be used to determine the age of a request and to ignore stale entries in scheduling logic.

Recommended Scheduling Pattern

Due to the reactive nature of the negotiation mechanism, scheduling decisions must be implemented incrementally. Since onNegotiate() can only accept or refuse the current request, it is not possible to directly select a specific request from the queue.

A recommended pattern is therefore to combine queue inspection, selective acceptance, and retry-based prioritization.

Pattern Overview

  1. Enable queue inspection
    Set QueueRequest to true to access the global queue and allow onQueue() to review incoming requests.
  2. Evaluate priority
    In onQueue() and/or onNegotiate(), evaluate all pending requests using available data such as:
    • time (arrival order)
    • value (custom priority)
    • agentreference or interfacereference (context-specific logic)
  3. Accept only the best candidate
    In onNegotiate(), compare the current request with the rest of the queue:
    • If the current request is the preferred one → accept
    • Otherwise → refuse
  4. Rely on retry behavior
    Refused agents will retry negotiation. Over time, higher-priority requests will reach the top of the queue and be accepted.
  5. Coordinate execution
    Route accepted requests through a local internal interface to ensure consistent execution and avoid resource conflicts.

Example Strategy

A simple priority strategy could be:

  • Prefer the request with the highest cost (stored in value)
  • Consider only negotiations within a timeout time
  • Wait until there is a queue of agents

This pattern allows the resource agent to implement flexible scheduling strategies within the constraints of the negotiation model. By combining queue visibility with selective acceptance and retry-based prioritization, it is possible to approximate optimal execution order in a fully distributed and reactive system.

Example: Queue-based scheduling with cost selection

In the following example, a resource interface waits until three agents have initiated negotiation. Each agent provides a cost value, which is stored in the queue.

When all three requests have arrived within a given time window, the resource agent selects the request with the highest cost and accepts it, while the others are refused and must retry.

$include 'system:queue.inc'
program Queue;
var constant TIMEOUT:=1050 : integer;
procedure printQueue;
var i:=1:integer;
begin
writeln('queue ', startindex(queue), ' - ', endindex(queue));
writeln('|INDEX | Object name | Interface ID | Time | Value |');
writeln('|------|---------------------|---------------------------------------------------------|---------|--------|');
foreach q in queue do
begin
write('| ', space(5, inttostring(i)), '| ');
write(space(20, q.agentreference.name + '.' + q.interfacereference.name), '| ');
write(space(55, q.interfacereference.ID), ' | ');
write(space(8, inttostring(q.time)), '|');
write(space(8, inttostring(q.value)), '|');
writeln();
i:=i+1;
end;
end.
// Wait for num agents that negotiate with us
function waitForAll(num:integer) : boolean;
var counter:=0, items:=0: integer;
var now : integer;
begin
now:=queue[startindex(queue)].time;
foreach item in queue do
begin
items:=items+1;
if item.value<>0 AND (item.time + TIMEOUT)>now then
counter:=counter+1;
end;
if items = num AND counter = items then begin
waitForAll:=true;
end;
else waitForAll:=false;
end.
// Check if the first item has the highest cost (best)
function isFirstBest() : boolean;
var firstCost: integer;
begin
firstCost:=queue[startindex(queue)].value;
foreach item in queue do
begin
if item.value>firstCost then begin
isFirstBest:=false;
exit;
end;
end;
isFirstBest:=true;
end.
function onNegotiate(Planning : boolean; a: Reference; i:Reference): integer;
begin
// Wait for all 3 parts to be in the queue
if waitForAll(3) then begin
// Check if the one that negotiataes now is the best one
if isFirstBest() then begin
// Accept the negotiation
onNegotiate:=1;
queue[1].value:=-1;
exit;
end;
end;
// printQueue();
// Refuse
onNegotiate:=-1;
end.
// Executed just before onNegotiate
function onQueue():boolean;
begin // Save remote interface variable value cost in the queue list as value
queue[startindex(queue)].value:=remoteinterface.cost;
end.
Note
This example demonstrates how scheduling decisions can be implemented using queue inspection and selective acceptance. Since only the current request can be accepted, lower-priority requests are refused and must retry until the preferred request reaches the top of the queue.
The TIMEOUT is used to ensure that only recent requests are considered. This prevents outdated requests from blocking the scheduling logic in a real-time system.
